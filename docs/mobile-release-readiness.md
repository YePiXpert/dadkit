## Run before sending an APK

```powershell
npm run test
npm run lint
npm run build
npm run mobile:android:handoff
npm run mobile:handoff:screenshots
npm run mobile:handoff:store-screenshots
npm run mobile:handoff:verify
```

After `npm run mobile:handoff:verify`, send the tester the ZIP at
`dist/mobile-handoff/dadkit-1.3.0-mobile-handoff.zip` or open
`dist/mobile-handoff/index.html` and use the direct APK link.
If only the existing handoff folder needs to be re-zipped, run
`npm run mobile:handoff:archive`.

Optional installed-APK checks:

```powershell
npm run mobile:android:install
node scripts/verify-android-webview-route.mjs https://localhost/settings/index.html WebDAV
node scripts/verify-android-webview-route.mjs https://localhost/privacy/index.html WebDAV
node scripts/verify-android-webview-route.mjs https://localhost/support/index.html GitHub
```

123pan WebDAV acceptance:

```powershell
npm run webdav:verify:prompt
npm run mobile:android:webdav:verify:prompt
```

The prompt commands ask for credentials at runtime and restore the previous
shell environment after they exit. Do not paste 123pan usernames, app
passwords, Apple signing credentials, or App Store Connect keys into commits,
docs, issue text, screenshots, or shared logs.

The handoff command rebuilds the debug APK and writes a tester-friendly package
under `dist/mobile-handoff/` with the APK, SHA-256 checksum, metadata, and a
short README plus `tester-guide.md`. It also writes `dist/mobile-handoff/index.html` as a
tester-friendly overview page with the image2-generated
`resources/store/dadkit-handoff-cover.png` visual cover and the 1024x500
`resources/store/dadkit-google-play-feature.png` feature graphic draft. The
directory is generated output and should not be committed.

The screenshot command starts the local production server, captures real mobile
screens for the core DadKit routes, and writes them under
`dist/mobile-handoff/screenshots/`.

The store screenshot command captures 10 real app screens at `430x932@3x` and
writes App Store 6.9-inch screenshot drafts under
`dist/mobile-handoff/store-screenshots/app-store-6-9/`. The generated PNGs are
`1290x2796`, matching the 6.9-inch portrait screenshot slot.

`npm run mobile:handoff:verify` checks the APK checksum, required native
project files, handoff index, image2 cover PNG dimensions, screenshot manifest,
12 screenshot files, screenshot overflow/diagnostic status, App Store screenshot dimensions/diagnostics, Google Play feature graphic dimensions/color type, and the shareable handoff ZIP contents. On
success it writes
`dist/mobile-handoff/readiness-report.md`,
`dist/mobile-handoff/readiness-report.json`, and refreshes
`dist/mobile-handoff/dadkit-1.3.0-mobile-handoff.zip`.

## Android release later

The current APK is a debug build for local installation and testing. Android's
debug certificate is generated by build tooling and is not accepted by most app
stores, including Google Play. A long-term Android release needs a release
keystore, release APK or AAB generation, keystore backup, and signing
documentation.

Release build entry points are already wired, but intentionally require
keystore values from the local shell:

```powershell
$env:DADKIT_ANDROID_KEYSTORE_PATH="<absolute path to release keystore>"
$env:DADKIT_ANDROID_KEYSTORE_PASSWORD="<keystore password>"
$env:DADKIT_ANDROID_KEY_ALIAS="<key alias>"
$env:DADKIT_ANDROID_KEY_PASSWORD="<key password>"
npm run mobile:android:release
npm run mobile:android:release:aab
Remove-Item Env:DADKIT_ANDROID_KEYSTORE_PATH
Remove-Item Env:DADKIT_ANDROID_KEYSTORE_PASSWORD
Remove-Item Env:DADKIT_ANDROID_KEY_ALIAS
Remove-Item Env:DADKIT_ANDROID_KEY_PASSWORD
```

Do not commit keystore files, keystore passwords, key aliases if private, or
release signing screenshots/logs.

## TestFlight later

The iOS project is ready to hand to macOS/Xcode, but actual TestFlight upload
still requires:

- Apple Developer Program membership.
- App Store Connect app record for `DadKit`.
- Signing team/provisioning for `com.yepixpert.dadkit`.
- macOS with Xcode, or Xcode Cloud / another macOS build path.
- Beta app description, feedback email, privacy URL, support URL, and export
  compliance answers.
- Non-secret metadata drafted in `docs/mobile-store-metadata.md`.

Apple's current TestFlight flow allows up to 100 internal App Store Connect
users and up to 10,000 external testers. TestFlight builds can be tested for up
to 90 days, and the first build added for external testing is sent to App
Review.
